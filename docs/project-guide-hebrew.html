מדריך הפרויקט — אוטומציית ParaBank ב־Playwright

תיעוד בעברית להכנה לראיון / הצגה: מבנה, הרצה, קונפיגורציה, סימונים (אנוטציות), והגיון ארכיטקטוני.

מטרת הפרויקט

הפרויקט הוא מסגרת בדיקות מוכנה לייצור סביב אתר הדמו ParaBank (parabank.parasoft.com): תרחישי UI, API, וזרימת קצה־לקצה (E2E) לפי מסמך הדרישות ב־objectives/playwright.txt.

שורת היעד מהמטלה (באנגלית, לתרגום רעיוני):

«כל ה־assertions חייבים לאמת: ולידציה, קודי סטטוס, מבנה תגובה, עקביות UI, נכונות נתונים»

את המיפוי המעשי לאותם עקרונות רואים ב־tests/e2e/support/api-assertions.ts וב־objectives/assertion-strategy.md (באנגלית).

דפדפנים

בהתקנה ראשונה (או אחרי עדכון Playwright) יש להריץ מהשורש:

npx playwright install

בלי דפדפן מותקן, טסטים שדורשים דפדפן ייכשלו עם הודעה על חסר executable.

תרחיש ה־E2E המרכזי

בקובץ tests/e2e/e2e.banking-journey.spec.ts מבוטאת הרצף:

  1. איפוס מדאטה־בייס הדמו (API)
  2. רישום משתמש חדש (UI)
  3. התנתקות
  4. התחברות כמשתמש הדמו john/demo (UI)
  5. קבלת מזהה לקוח דרך API
  6. משיכת חשבון קיים (API, לדוגמה חשבון 12345)
  7. יצירת חשבון CHECKING ב־curl (כפי שנדרש במטלה)
  8. וידוא שהחשבון החדש מופיע ב־UI (סקירת חשבונות)
  9. העברת כספים בין חשבונות (UI)
  10. אימות יתרות מעודכנות (API)
  11. התנתקות (UI)

בדיקות נוספות

  • API — api.parabank.spec.ts: YAML של OpenAPI, XML של לקוח/חשבונות, מבנה תגובה.
  • יתרות — api.balances.spec.ts: העברה ב־API ושינוי יתרות מספרי.
  • UI ממוקד — דף בית, התחברות, הרשמה, יציאה, העברה, יצירת חשבון (רבים מתויגים @component).

כל שלב ב־E2E עטוף ב־test.step כדי שדוח ה־HTML של Playwright יציג שלבים מתועדים (קל יותר להסביר בראיון מה נכשל).

עץ לוגי של התמיכה בבדיקות

  • tests/e2e/support/parabank.constants.ts — כתובות, מזהי דמו, עזרי פרסור XML.
  • tests/e2e/support/api-assertions.ts — פונקציות expect* למפתחי סטטוס, מבנה XML, הודעות העברה.
  • tests/e2e/support/db.helpers.ts — resetDemoDatabase (cleanDB + initializeDB עם קוד 204).
  • tests/e2e/support/parabank-flow.helpers.ts — צעדי עסק אמיתיים (רישום, curl, העברה ב־UI, בדיקות API משותפות) — מקור יחיד לאמת בין E2E לטסטים קטנים.
  • tests/e2e/support/auth.helpers.ts — התחברות דמו קצרה.
  • global-setup.ts — איפוס לפני כל הרצת סוויטה (הכנת סביבה יציבה).

ניתן גם קישורי re-export תחת tests/support/ אם מייבאים מנתיב tests/ ולא מ־tests/e2e/.

playwright.config.ts — הנקודות החשובות

  • testDir: './tests/e2e' — כל קבצי ה־spec נמצאים שם.
  • globalSetup — טוען את global-setup.ts לאיפוס ParaBank לפני הריצה.
  • fullyParallel: true — מקביליות ברמת הקבצים; בתוך תרחישים שצריכים סדר (כמו ה־describe הסיריאלי ב־E2E) Playwright מכבד serial.
  • use.baseURL — https://parabank.parasoft.com כך ש־page.goto('/parabank/...') יחובר לאתר האמיתי.
  • use.trace: 'on-first-retry' — טרייס בכישלון אחרי retry (חוסך מקום בדרך כלל).
  • projects — כרגע מופעל Chromium בלבד; Firefox/WebKit מושבתים בהערות.
  • CI — forbidOnly, retries, workers מותנים ב־process.env.CI.

איזה «אנוטציות» בשימוש (ובפירוט טכני)

תג @component (Playwright)

מוגדר על טסטים או על test.describe — בפרויקט משמש לסמן פרוסות עצמאית (רישום, התחברות, API וכו׳) שניתן להריץ יחד עם npm run test:component (--grep @component).

לא נתנו תג כזה לזרימת ה־E2E המלאה — כדי שיהיה ברור מהו «שער» אחד (test:e2e) בלי לבלבל עם מסנני תגים.

test.describe.serial

בתוך הקובץ של הזרימה המלאה, ה־describe מסומן כסיריאלי. בפועל יש טסט אחד שמכיל את כל הצעדים (עם test.step), כך שהסדר נשמר והבלבול של טסטים מקבילים על אותו דמו מצומצם.

test.step('שם', async () => { ... })

אינו אנוטציה של TypeScript — זה API של Playwright שמוסיף שכבת דיווח בתוך טסט יחיד: בדוח רואים אילו שלבים עברו לפני כישלון (נוח לראיון ול־Root Cause).

הערות JSDoc (/** ... */)

ב־api-assertions.ts ובקבצי spec נוספים — מפנות למסמכי objectives/assertion-strategy.md. אלו לא משנות התנהגות בזמן ריצה; הן תיעוד למפתח.

למה בחרנו בשיטה הזו ולא באחרת?

1. parabank-flow.helpers.ts + טסטים דקים

חלופה: להעתיק את אותו קוד UI/API לכל קובץ spec.
בחירה: לוגיקה משותפת במקום אחד, והקבצים המפוזרים רק קוראים לפונקציות.
סיבה: תחזוקה אחת כשהאתר משתנה; פחות סתירות בין E2E לבדיקות משנה; עדיין אפשר להריץ פרוסות עם @component.

2. תג @component + --grep במקום פרויקטים כפולים ב־config

חלופה: מספר projects ב־Playwright (למשל «מלא» מול «מצומצם»).
בחירה: תג אחיד וסקריפט npm פשוט.
סיבה: פחות כפילות בהגדרות דפדפן; קל להסביר; שינוי מינימלי ב־playwright.config.ts.

3. test.step בתוך טסט E2E אחד (ולא שרשרת של 10 טסטים סיריאליים)

חלופה: 10 פונקציות test() סיריאליות עם מצב משותף.
בחירה: טסט אחד אטומי מבחינת «האם הזרימה הושלמה», עם שלבים לדוח.
סיבה: בתרחיש בנקאי קשה לפרק לטסטים נפרדים בלי להריץ איפוס DB ביניהם או לסמוך על סטייט דפדפן בין קבצים — טסט אחד מבטא טוב יותר story אחת end-to-end.

4. globalSetup + resetDemoDatabase בטסטים שצריכים מצב ידוע

סיבה: ParaBank הוא דמו משותף; איפוס לפני ריצה ולפני טסטים רגישים מפחית ריצות הפיכות עקב זיהום מצב מריצות קודמות.

5. העדפת expect2xxWithStatus ומבני XML

במקום res.ok() בלבד — כדי לעמוד במפורש בדרישת קוד סטטוס ומבנה תגובה מהמטלה ולתעד זאת בראיון.
